#  Система учёта для небольшого металлообрабатывающего производства

Этот проект я делал, чтобы понять, как на реальных заводах отслеживают работу станков, управляют заказами и считают эффективность. Вдохновлялся промышленными системами — где OEE (Overall Equipment Effectiveness) — почти святое.

Всё написано на Java, без лишней магии: только Spring Boot, PostgreSQL и честный код. Главное — система умеет **автоматически считать OEE** и отдавать его через REST API.


##  Технологии

- **Java 21 + Spring Boot 3** — основа всего
- **PostgreSQL 17** — с индексами и оптимизацией «под боевые» запросы
- **JWT** — авторизация без излишеств
- **MapStruct** — маппинг DTO без reflection
- **Docker** — запуск в один клик
- **Swagger** — документация прямо в браузере
- **Flyway** — миграции под контролем
- **Prometheus + Grafana** — базовый мониторинг (JVM, HTTP, CPU и т.д.)
- **JUnit 5 + TestContainers** — простые, но рабочие тесты



##  Как запустить

```bash
git clone ...
mvn clean package
docker compose up --build
```

И всё готово:

- API: `http://localhost:8080`
- Документация: `http://localhost:8080/swagger-ui.html`
- Grafana: `http://localhost:3000` (логин/пароль: `admin/admin`)
- Prometheus: `http://localhost:9090`

> Совет: зайдите в Grafana → **+ Create → Import** → введите ID **12856** → выберите Prometheus как источник. Получите готовый дашборд по Spring Boot.



##  Что умеет?

### Учёт производства
- Регистрирую партии металла (сплав, вес, поставщик)
- Добавляю станки (CNC, токарные и др.)
- Управляю заказами: *ожидание → в работе → завершено*

### Мониторинг станков
- Станки сами шлют статусы (температура, вибрация, состояние)
- Приём асинхронный: сразу отвечаю `202 Accepted`, обработка — в фоне
- Если приходит `ERROR` — в логе появляется предупреждение

### Расчёт OEE
Считаю по формуле:

```
OEE = Доступность × Качество
```

- **Доступность** — сколько времени станок реально работал
- **Качество** — доля годных деталей

Пример запроса:
```http
GET /machines/1/oee?from=2025-11-01T00:00:00&to=2025-11-01T23:59:59
```

Ответ:
```json
{
  "availability": 0.75,
  "quality": 0.92,
  "oee": 0.69
}
```


##  Мониторинг

Добавил **базовую визуализацию через Prometheus + Grafana**:
- JVM (память, потоки, GC)
- Загрузка CPU
- HTTP-запросы (RPS, время ответа, ошибки)
- Состояние пула БД

Пока OEE не отображается в Grafana — но это в планах. А так уже можно следить, не «задыхается» ли приложение под нагрузкой.



##  Тесты

Написал **простые, но осмысленные тесты**:
- Проверяю CRUD-операции с учётом авторизации
- Тестирую ошибки (но не все ибо лень, проект то учебный :) )
- Использую **TestContainers**, чтобы тесты работали против настоящего PostgreSQL

Структура продумана, но не перегружена — легко расширять.


##  Почему так сделано?

- Никаких фреймворков-«чудо-ящиков» — только то, что можно понять и починить самому.
- Избегаю N+1 через `@EntityGraph`.
- DTO — через `record`: коротко, безопасно, без boilerplate.
- Асинхронность — через `@Async`, но с ограничением пула, чтобы не упасть под нагрузкой.

Проект задуман как **основа для роста**: можно добавить Kafka, расширенную аналитику, мобильный клиент или интеграцию с 1С.

## Что дальше?

- Добавить **Performance** в расчёт OEE → полная формула: `Availability × Performance × Quality`
- Вынести агрегацию OEE в `@Scheduled` задачу
- Экспортировать OEE в Prometheus → отображать в Grafana
- Настроить **алерты** (например, OEE < 0.6 или ошибка станка)
- Подключить **Kafka/RabbitMQ** для надёжной обработки статусов


Это мой учебный, но **практически ориентированный** проект. Он не идеален — но он **работает**, **тестируем** и **готов к развитию**.
